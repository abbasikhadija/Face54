# Engineering decisions

## M4 — Production solving pipeline (2026-10-23)

**Problem:** M3 validated input but stopped before computing a solution. The original one-shot worker had no request identity, runtime protocol checks, cancellation/retry or protection against a returned solution belonging to another input.

**Choice:** Keep cubejs and the independent geometric move implementation. Split preparation/search in the adapter, and add small ordinary modules for the typed protocol/handler and main-thread request lifecycle. A solve request carries a positive unique ID and canonical state. Progress distinguishes preparation/search; results carry ID, original state, moves and measured times; errors use bounded codes. Validate input on both sides. Reject malformed messages, invalid physical input, wrong snapshots, invalid timings and unsupported/incorrect moves. Independently apply returned moves in the worker and again before main-thread publication. Parsing alone remains insufficient. Already-solved input returns zero moves/times without table initialization.

**Lifecycle:** One active request per client. Capture the exact request object and ID so replaced, cancelled or disposed callbacks cannot publish. Unmount on edit/navigation; do not persist solutions. Every worker is terminated after success, failure, cancellation, disposal or a 60-second watchdog timeout. Retry creates a new worker. Alternative: retain a warm shared worker and multiplex consumers. Rejected for this small flow because it adds lifecycle/state complexity and retains large tables. Accepted cost: cold retries/rechecks initialize again. Synchronous cubejs cannot process a cancel message during work, so termination is the actual cancellation mechanism.

**UI/boundary:** Successful Check cube starts local solving automatically. Show preparation/search status, Cancel, recoverable errors/Try again, verified move count or already-solved confirmation. Keep colors unchanged throughout. Focus terminal status headings; retain face correction controls. M5 physical turn guidance is not implemented, and no preview/turn is recorded. Both existing demo and M0 proof now use the same typed client without changing their existing exploration/mesh behavior; retaining an untyped legacy worker path was considered and removed to keep one trust boundary.

**Verification:** New handler tests execute 103 deterministic actual solver cases. Injectable transport tests cover creation/post/decode errors, initialization/search/verification failures, malformed output, stale IDs/captured callbacks, replacement/cancellation/disposal, watchdog cleanup and retry. Production browser tests observe real worker requests/results and independently apply returned moves; verify complete UI entry, desktop/mobile, solved fast path, responsive cancellation, navigation/edit invalidation, malformed/impossible requests, recovery and rejected wrong output. Fault-injected output tests are distinguished from real solver runs. Final counts/timings and unchanged release risks are in M4_REPORT.md. No dependencies added; physical cube trials remain pending.

## M0 — Solver and renderer integration (2026-10-23)

**Problem:** A solver and a visually plausible cube can disagree about face order, mirroring, or move direction.

**Choice:** cubejs 1.3.2 for its existing Kociemba solver; Three.js 0.186.1 for rendering. React 19.3.1, Vite 8.3.5, TypeScript 7.0.2; exact resolved dependencies are in package-lock.json. No custom solving algorithm. A small integer geometry implementation independently applies outer face turns and maps 54 sticker planes to URFDLB facelets. The renderer is established Three.js; the cube-specific adapter is our responsibility.

**Alternative:** cubing.js / TwistyPlayer. Official docs place scramble setup (`experimental-setup-alg`) and several playback features behind experimental APIs. Registry evaluation returned cubing 0.66.1 with `MPL-2.0 OR GPL-3.0-or-later`. It was evaluated through documentation/metadata, not installed or browser-tested. Three.js offers direct inspection of arbitrary facelet colors without depending on experimental cube-player state APIs. Accepted trade-off: we own and must test the 54-sticker adapter and any future layer animation. M0 uses discrete seeking, expressly allowed by the spec. No experimental renderer APIs required.

**Coordinates:** right-handed x=R, y=U, z=F. A face grid is viewed from outside; rows go down. URFDLB order matches cubejs's published net. The six above/right landmarks in PROJECT_SPEC.md are retained exactly: F U/R, R U/B, B U/L, L U/F, U B/R, D F/R. Clockwise is -90° around the outward normal; inverse is three quarter-turns and `2` is two. Fixed colors U white, R red, F green, D yellow, L orange, B blue. Automated agreement covers all 18 turns, the recorded scramble, and 100 seeded legal scrambles with every solution boundary. Physical orientation testing is pending; no physical trial is claimed.

**Verification:** independent sticker rotations agree with cubejs's cubie implementation; all actual mesh world positions, normals and material colors reconstruct the same facelets. Solutions are rejected unless independent application ends solved. This checks all six faces, including those hidden by the camera. Pixel/browser evidence complements those assertions; a screenshot alone cannot establish all-face correctness.

**Licensing:** installed cubejs, Three.js, React and Vite license files/metadata are MIT. Preserve upstream notices when redistributing. cubing was not shipped. No project-wide legal license was invented.

**Compatibility:** installed Three.js source explicitly requires WebGL2 (WebGL1 unsupported since r163). Vite handles cubejs CommonJS and worker bundling. Test production on a non-root `/Face54/` path; do not infer public GitHub Pages deployment. Node 22.14.0 used. Firefox/Safari/mobile hardware coverage is not established by Chrome/Edge tests.

**Dependency risk:** cubejs depends on npm ^6.0.0, even though its entry point imports only lib/cube and lib/solve. `npm audit --json` recorded 42 findings (12 moderate, 27 high, 3 critical), attributable to that legacy dependency tree. Do not claim the dependency tree is clean. The worker bundle does not ship the npm CLI; this limits browser exposure but does not remove installation/tooling risk. Replacing/patching that packaging dependency or choosing a maintained solver must be resolved before release. Audit snapshot: docs/npm-audit.json. Avoid automatic `audit fix --force`, which proposes changing solver versions without compatibility proof.

**Performance:** one Node verification run: preparation 3646.46 ms; solve min 0.013 ms, mean 95.48 ms, max 949.01 ms across 103 states (includes solved/one-move). These are local observations, not guarantees or shortest-solution claims. Build observed 848 ms, main chunk 747.05 kB / 200.68 kB gzip and worker 19.55 kB; Vite emits its >500 kB warning. Cold browser results are recorded in M0_REPORT.md. The M0 renderer preserves its drawing buffer for diagnostic pixel readback; reconsider this cost for production.

Sources checked: [cubejs API and facelet net](https://github.com/ldez/cubejs), [TwistyPlayer experimental API documentation](https://js.cubing.net/cubing/twisty/), [Three.js renderer source](https://github.com/mrdoob/three.js/blob/dev/src/renderers/WebGLRenderer.js), [WCA move notation](https://www.worldcubeassociation.org/regulations/#article-12-notation). Installed package source and licenses are the version-specific evidence.

## M0 compatibility correction

Production browser testing exposed cubejs's `this.Cube || require('./cube')` access failing when top-level `this` is undefined in a module worker. `vite.config.ts` applies one guarded pre-transform to cubejs/lib/solve.js, selecting its existing CommonJS `require('./cube')` branch. It runs for app and worker builds without editing node_modules or upstream algorithms, and throws if the expected source changes. Trade-off: a version-sensitive compatibility patch requiring re-verification on upgrade. The production browser tests are the regression checks. The preview script also explicitly configures the test base path; setting only the build CLI base did not configure the preview server's base.

## M1 — Minimal design foundation (2026-10-23)

**Problem:** M0 had a correct diagnostic harness but no coherent entry experience. M1 must establish a useful foundation without implementing later milestones.

**Choice:** Add welcome, preparation and a working demo around the existing verified state/solver integration. Plain React components and CSS custom properties use the spec's graphite palette, warm accent and a system sans-serif. One main action per screen; no dashboard panels, decorative animation, remote assets/fonts or extra dependencies. Preparation explains the home orientation but clearly states that color entry is pending M2. The demo retains M0's manual state seeking; it is not physical move-confirmation playback (M5).

**Navigation:** Small hash-based screens (`#prepare`, `#demo`, home) support Browser Back and direct links on static hosting without a router package or server rewrites. Screen titles receive focus on navigation, while the initial welcome preserves normal keyboard entry. Native links/buttons and a range input provide keyboard interaction; a skip link and visible focus states support navigation. Alternative: pathname routing would need additional Pages fallback handling for only three screens. Accepted trade-off: a small hand-written screen switch, to revisit only if routing grows.

**Renderer:** Keep the exact M0 `makeCube`/`readCube` sticker mapping. Use the installed Three.js OrbitControls to orbit only the camera, with arrow-key camera controls and explicit reset. Disable pan, zoom, inertia and automatic rotation. No animation loop runs while idle; redraw on state, camera or resize changes. A ResizeObserver fits the canvas to its container and pixel ratio is capped at 2. Add a dark internal cube body outside the sticker group, so mesh serialization still reads precisely 54 sticker planes. Dispose controls, listeners, observers, geometries and materials when the React view unmounts. Diagnostic mode retains buffer preservation for M0 checks; product mode uses a transparent canvas with no preserved drawing buffer. Alternative: rotating the sticker group could redefine the coordinates used for verification; moving the camera preserves them. No experimental APIs required.

**Scope preservation:** Retain the M0 harness at `?proof=1` with its regression tests, rather than leaving raw facelets/performance numbers in the product flow. Start the real solver only after entering the demo, and terminate the one-request worker when leaving. No complete input/editor/persistence, physical validator, production worker protocol or physical step-confirmation flow has been built.

**Verification:** TypeScript/build, existing 21 correctness tests, production Chrome/Edge M0 integration, desktop/mobile journeys, keyboard focus/slider/camera, pointer drag/reset, emulated touch drag/tap/reset, responsive resizing, reduced-motion CSS, unavailable WebGL2 and failed worker messages. Screenshots are visually inspected and saved in docs/screenshots. A touch test initially mixed raw CDP drag injection with a separate Playwright touch session and scrolled during click delivery. The corrected test keeps both gestures on one CDP session, positions the reset target first, lets the compositor settle the scroll, and waits for click delivery before taking a screenshot. Camera reset works for pointer, keyboard and emulated touch. This is browser emulation, not real mobile hardware acceptance. Palette contrast against #10151C: text 16.48:1, muted 8.33:1, accent 9.40:1; accent-button text uses the reversed 9.40:1 pair. No full assistive-technology audit is claimed.

**Trade-offs / risks:** The main chunk grows from ~747 kB to ~779 kB (~209 kB gzip), primarily with camera controls and the shell; the existing Vite warning remains. Solver/worker code and the guarded module-worker compatibility transform remain unchanged. Legacy dependency findings, WebGL2 requirement, physical trials, and untested Firefox/Safari remain open. No new dependency was installed; resolving those release concerns is not disguised as an M1 design change.

## M2 — Cube input and orientation (2026-10-23)

**Problem:** Entry must preserve exactly which sticker was captured across incomplete faces, correction, navigation and refresh. A plausible 3D guide cannot establish grid orientation on its own.

**Canonical input:** Keep M0's URFDLB indices and export the shared Face type. Represent missing stickers as `Face | null` in InputDraft; six centers are fixed. Entry order is F/R/B/L/U/D. Explicit outside-view row/column mappings avoid mirrored per-screen grids and extra conversions. Incomplete or fully colored input is never called a valid solver state. Counts include centers and warn about excess without rejecting or repairing partial input.

**Orientation:** Retain the spec's landmarks: F U/R, R U/B, B U/L, L U/F, U B/R, D F/R. Verify using the installed upstream cubejs README net, independent literal coordinates for all slots, corner adjacency and actual perspective projections of all six poses. M0's solver/renderer regression remains. Physical cube confirmation is pending; automated evidence is not a physical trial.

**Reference:** First entry to a face in an editor session opens a solved standard-color reference. Only the camera moves to a prescribed pose; endpoint readback verifies all 54 actual mesh stickers remain solved. Disable inspection controls in this reference so users cannot disturb the prescribed view. Shrink it after the one-second transition, allow hiding/reopening, cancel animation on unmount, and skip motion when reduced motion is requested. New-face focus goes to the guide heading, so mobile navigation does not jump past it; hiding returns focus to entry. Text guidance remains available without WebGL2. No layer-turn code or animation dependency was added.

**Painting:** Palette selection does not paint. A sticker activation paints one slot; cyclic smart selection finds the next empty spot on the same face, without painting it or changing faces. UI and pure operations both protect centers. Keyboard focus updates the active slot; arrows move through editable positions and Enter/Space paints. Clear face preserves its center and other faces. Tabs and Previous/Next preserve incomplete work. No review net or physical validator (M3) is included.

**Persistence:** Version-1 `face54.draft` stores canonical facelets and current face only. Validate version, face, length, allowed values and all centers before restoration. Do not persist palette choice, active slot, guide visibility, animation, timestamps or solver results. Keep the draft at app scope across navigation. Save actual editable work; remove the key when none remains. Catch blocked getters/reads, writes/quota errors and deletion failures; explain how to retain memory-only edits. Malformed/future data is not silently interpreted. Physical validity is deliberately not required to restore unchecked input. A native modal confirms Start new cube only when work would be lost; Keep editing is focused by default and Escape cancels. A global storage framework and persistence of every UI detail were considered unnecessary. Cross-tab arbitration is not implemented.

**Scope:** The fixed demo and verified worker remain independent of entered colors. No input state is sent to the solver. M4 must bind real solutions to input revisions; this is not that production pipeline.

**Verification / refinements:** Unit tests cover every mapped slot, landmarks/corners, immutable corrections, centers, selection and defensive persistence. Browser tests enter all 48 editable stickers of the legal M0 fixture and compare restored facelets exactly; exercise guides with mesh readback, incomplete navigation, keyboard, emulated touch, counts, confirmation and storage failures. Screenshot review improved green-sticker label contrast (dark text) and empty-cell borders, and hid an offscreen skip-link capture artifact without removing keyboard access. All sticker text pairs measure at least 5.01:1; empty-cell boundary contrast is 3.22:1. No full screen-reader or real hardware acceptance is claimed.

The inherited M1 touch test occasionally lost compatibility clicks after raw CDP gesture injection. Its regression now verifies a native touch reset of a changed camera before injecting a drag, then verifies that the raw touch drag rotates the cube and keyboard reset restores it. This keeps both touch assertions without treating a following raw compatibility click as reliable automation; a real-hardware drag-then-tap sequence remains pending. The keyboard test waits for React's heading before the first Tab. No new application gesture handlers or retries were added. Existing 390×844 mobile coverage and M2 native touch painting checks remain.

No dependencies changed. Existing solver audit findings, WebGL2 requirement, bundle size, cold initialization and future real-cube acceptance remain release risks. See M2_REPORT.md for commands, final results and measured build output.

## M3 — Review and physical validation (2026-10-23)

**Problem:** Correct counts and a successfully parsed facelet string do not establish physical solvability. Input needs a safe correction path without data loss or invented diagnoses.

**Validation:** Add a pure renderer/solver-independent validator over the existing canonical slots. Stage checks: array shape and known colors; missing entries (stop before physical claims); fixed Western centers; nine of each color; exact oriented edge/corner identities; uniqueness; edge orientation sum modulo 2; corner orientation sum modulo 3; matching permutation parity. Corner identity matching accepts cyclic rotations only, rejecting mirrored corners even when the three colors look familiar. Return a discriminated result containing complete state/cubies or structured issue codes. Never mutate or repair input. Unexpected reader failures return internal_failure instead of exposing exceptions.

**Established representation:** Use the cubejs/Kociemba facelet-to-cubie order already verified by M0/M2, checked against installed cubejs 1.3.2 source and independent labeled geometry. Reference invariants: [Kociemba's cubie representation](https://kociemba.org/math/cubielevel.htm) and [the author's verify routine](https://github.com/hkociemba/RubiksCube-TwophaseSolver/blob/master/cubie.py). The application implements standard validation checks; it does not implement a new solving algorithm or import the referenced Python implementation. Every piece table group is tested to occupy one actual geometric cubie; all 48 non-center facelets occur exactly once.

**Library evaluation:** Tests show that cubejs.fromString parses a single flipped edge, a single twisted corner and an odd edge permutation, and asString round-trips each unchanged. Installed fromString has no uniqueness/orientation-sum/permutation-parity verification. Therefore neither parsing nor round-trip equality is accepted as validation. The existing solver adapter and demo worker are unchanged; M4 must explicitly use the validator before solving entered states.

**Error evidence:** Missing entries have exact positions. Invalid piece identities mark the whole two/three-sticker group; duplicate identities mark all repeated groups and report missing identities structurally. Excess counts mark editable entries of excess colors, excluding known-correct fixed centers. These are candidates to recheck, not claims that every marked sticker is wrong. Global flip/twist/permutation constraints have no position highlights: the evidence cannot identify the mistaken input. This deliberately trades highly specific-looking advice for mathematically justified guidance.

**Review and correction:** A flat outside-view U / L F R B / D net uses canonical slots directly, with color initials plus accessible full labels, completion/counts and a single Check cube action. Edit returns to the chosen face and marks evidence-supported groups. Check never edits or erases colors. Checked results and correction marks are transient and bound to a serialized facelet snapshot; color changes remove old evidence, and returning to review requires a new check. Persistence remains input-only with its existing schema. Alternatives considered: silently repairing input, trusting the library parser, or highlighting one guessed flipped sticker were rejected for correctness reasons.

**Milestone boundary:** A successful check confirms physical possibility of the entered colors, then stops with an honest note that entered-state solving is not yet available. It does not start a worker, create a placeholder solving flow or change the fixed demo. This is the intentional progressive-development boundary before M4, rather than prematurely implementing the full end-to-end journey.

**Verification/performance:** Validate 1,000 seeded legal states and compare decoded cubies with cubejs. Reject all specified impossible fixtures, every isolated edge flip, both isolated twists at every corner and every isolated pair swap of edges/corners; accept cancelling orientations and matching odd permutations. Browser checks cover net mapping, corrections, persistence, highlight scope, keyboard/touch, stale-result clearing and zero solver workers during review. Measured 1,000 legal validations total 144.85 ms (mean 0.145 ms) in a local Node run concurrent with browser checks; this excludes UI rendering and is an observation, not a guarantee. No dependencies added. Physical cube, non-Chromium and real hardware acceptance remain pending. See M3_REPORT.md for final results and unchanged release risks.
